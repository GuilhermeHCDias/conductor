## 1. O que é o Conductor

Aplicação **desktop (Electron + TypeScript + React)** que permite a **qualquer pessoa — inclusive quem não é desenvolvedor — escrever testes end-to-end**.

Por baixo dos panos, o Conductor **orquestra a CLI do Maestro**. Ele não reimplementa drivers de automação, não fala com o device diretamente e não inventa um formato próprio de teste. Ele é uma camada de produto sobre o Maestro.

**Analogia central:** o Conductor está para o Maestro Studio assim como um editor visual está para um editor de texto — mesma saída (`.yml`), muito menos cerimônia de entrada.

### 1.1 Por que existe (o problema)

O Maestro Studio já permite inspecionar a tela e gerar comandos, mas exige do usuário decisões de configuração que **não fazem sentido no nosso contexto**, porque o Conductor serve a **um único app** e **um único repositório**:

| Etapa que o Maestro Studio pede | O que o Conductor faz |
|---|---|
| Selecionar o `appId` | ✅ Fixo em constante: `com.vtex.pnp` |
| Selecionar o workspace / pasta de flows | ✅ Fixo: pasta `.maestro/` do repositório canônico |
| Descobrir seletores manualmente | ✅ Hover na tela espelhada → seletor sintetizado e validado |
| Escrever YAML na mão | ✅ Janela de IA que edita o `.yml` em tempo real |
| Versionar e distribuir o teste | ✅ Abre Pull Request direto da aplicação |

Cada etapa removida é uma barreira a menos para o usuário não-técnico.

### 1.2 Público-alvo

Pessoa de **QA, produto ou negócio** que conhece o app e sabe descrever um fluxo em linguagem natural, mas **não sabe (e não deveria precisar saber)** o que é `resource-id`, regex, YAML, branch ou pull request.

**Consequência de design, aplicável em toda a UI:** todo jargão técnico deve ter uma tradução em linguagem de produto na interface. O YAML continua sendo a saída canônica e fica visível para quem quiser, mas **nunca é o caminho obrigatório**.

## 2. Constantes de configuração ✅

Todas centralizadas em **um único módulo** (`src/shared/config.ts`), sobrescrevíveis por variável de ambiente. Trocar app ou repositório deve ser uma mudança de uma linha.

```ts
// src/shared/config.ts — fonte única de verdade
export const CONFIG = {
  /** Package name (Android) / bundle id (iOS) do app sob teste. */
  APP_ID: process.env.CONDUCTOR_APP_ID ?? 'com.vtex.pnp',

  /** Repositório canônico que contém os testes e2e. */
  REPO_URL: process.env.CONDUCTOR_REPO_URL ?? '<definir>',

  /** Branch base para novos PRs. */
  REPO_BASE_BRANCH: process.env.CONDUCTOR_BASE_BRANCH ?? 'main',

  /** Pasta, dentro do repo, onde vivem os flows. */
  FLOWS_DIR: '.maestro',

  /** Extensões reconhecidas como flow. */
  FLOW_EXTENSIONS: ['.yml', '.yaml'] as const,
} as const;
```

**Regras:**

- ⚠️ **Nunca** hardcode `com.vtex.pnp` fora deste módulo. Sempre importe `CONFIG.APP_ID`.

- ✅ **`com.vtex.pnp` é idêntico no Android (package name) e no iOS (bundle identifier)** — confirmado pelo dono do produto.

  Consequência boa, e vale explicitar porque simplifica código em vários pontos: `APP_ID` é uma **`string` simples**, não `{ android, ios }`. O header do flow sai igual nas duas plataformas, sem condicional:

  ```yaml
  appId: com.vtex.pnp
  ```

  Não existe caminho de código que precise escolher `appId` por plataforma. Se um dia divergirem, este é o ponto de mudança — e aí `APP_ID` vira um objeto e o Gateway escolhe pela plataforma do device conectado.

- ⏸️ **`REPO_URL` será preenchido depois.** Decisão do dono do produto: não bloqueia o início.

  **Não bloqueia** o `MaestroGateway`, o mirror de device, o hit-test, a síntese de seletor nem o editor — ou seja, os passos 2 a 7 da seção 13. **Bloqueia apenas** `RepoService`, `FlowIndex` e `GitHubService` (passo 8).

  🔷 Até lá, desenvolver contra uma **pasta `.maestro/` local de fixtures**, com flows de exemplo. Isso é bom por si só: dá um alvo determinístico para os testes do `FlowIndex` e do parser, independente de rede e de credencial. Manter as fixtures no repo mesmo depois que a `REPO_URL` chegar.

## 3. O app sob teste

**React Native.** Isso não é um detalhe: define a estratégia inteira de captura de elemento (seção 5).

O que importa saber sobre RN + Maestro (verificado na documentação oficial):

- Maestro testa o **binário final**. Não exige pacote npm, nem instrumentação, nem alteração no código JS/TS do app. ✅ Não vamos pedir mudanças no app da VTEX.
- Mapeamento de props RN para atributos nativos:

| Prop React Native | Android | iOS |
|---|---|---|
| `testID` | `resource-id` | `accessibility-id` |
| `accessibilityLabel` | `content-desc` | `label` |

- **Consequência prática:** `testID` é a única prop que produz um seletor **estável e cross-platform**. É por isso que a estratégia de síntese de seletor (seção 5.4) prioriza `id:` acima de tudo.
- ⚠️ **iOS, componentes aninhados:** o RN pode "engolir" eventos de toque em hierarquias profundas. A correção documentada é `accessible={false}` no container externo e `accessible={true}` no elemento alvo. Se um elemento aparece na árvore mas o tap não funciona, é este o suspeito número um.
- ⚠️ **Bug conhecido (Maestro #3056):** no iOS, elementos podem **sumir da árvore de acessibilidade após navegação de volta**, e o Maestro deixa de encontrá-los por `testID`/`text`. Se o Conductor apresentar tela vazia ou incompleta depois de um "voltar", este é o suspeito. Tratar como condição esperada na UI, não como crash.

## 4. Integração com o Maestro

### 4.1 Formato de um flow ✅

Um flow é um `.yml` com dois documentos YAML separados por `---`: um **header** de configuração e uma **lista de comandos**.

```yaml
appId: com.vtex.pnp        # header — sempre CONFIG.APP_ID
---
- launchApp
- tapOn:
    id: "login_button"
- inputText: "usuario@vtex.com"
- assertVisible: "Bem-vindo"
```

### 4.2 Comandos da CLI que o Conductor usa

| Comando | Uso no Conductor |
|---|---|
| `maestro test <arquivo\|pasta>` | Executar um flow ou a suíte inteira |
| `maestro test -c` | Modo contínuo: re-executa ao salvar o arquivo |
| `maestro hierarchy` | Ler a view hierarchy do device (JSON puro a partir da v2.6.0) |
| `maestro start-device` | Subir emulador/simulador |
| `maestro record` | Gravar vídeo da execução (feature futura) |
| `maestro check-syntax` | Validar YAML antes de rodar / antes de abrir PR |
| `maestro mcp --no-viewer` | ⚠️ **Não é invocado por nós.** É subprocesso do Claude Code, configurado via `--mcp-config` (4.3). Serve só a camada de IA |

⚠️ Toda invocação **nossa** leva `--no-reinstall-driver` e `MAESTRO_CLI_NO_ANALYTICS=1`. O `mcp` leva a env var e `--no-viewer`, mas não a flag de driver — ela não existe nesse subcomando. Ver 4.4 e a regra 10 da seção 12.

### 4.3 Duas camadas, duas fontes ✅ — decisão tomada

**A UI fala com a CLI crua. A IA fala com o `maestro mcp`.** A fronteira não é meio-termo por indecisão — segue um critério, definido em 4.3.1.

| Camada | Fonte | Por quê |
|---|---|---|
| **UI** — hit-test, mirror, síntese de seletor | `maestro hierarchy` cru, via `MaestroGateway` | Precisa da árvore **completa** |
| **IA** — Claude Code (seção 6) | `maestro mcp` via `--mcp-config` | Formato compacto é o ideal para LLM; `cheat_sheet` de graça; sessão persistente |

#### 4.3.1 O critério ⭐

> **MCP só compensa quando há um modelo numa das pontas.**

Um LLM precisa de uma camada que **descreva capacidades** a ele: "existe uma ferramenta `inspect_screen`, aceita `device_id`, devolve a árvore da tela". Padronizar essa descrição é exatamente o que o MCP faz (ver o glossário, seção 11.1).

Nossa UI não é um modelo — é código React que quer uma estrutura de dados para calcular hit-test. Passar isso por um protocolo cuja função é descrever capacidades a um LLM adiciona serialização e camada sem devolver nada. Chamada de função direta resolve.

Esse critério é o que decide qualquer dúvida futura do tipo "isso deveria ser MCP?".

#### 4.3.2 Por que a UI não usa o MCP

1. **⭐ A árvore crua é melhor para nós que a compacta.** O `inspect_screen` é **lossy**: descarta nós de tamanho zero e containers vazios, e abrevia chaves. Ótimo para LLM — **perda de informação para hit-test**. Ver 5.2.
2. **Sem contrato de estabilidade.** As ferramentas MCP não são API versionada. Acoplar a UI inteira a elas é o risco do Studio (4.5). Restrito ao painel de IA, uma mudança quebra **uma feature**, não o produto.
3. **A CLI é a superfície mais estável que o Maestro oferece** — é o contrato público da ferramenta.

⏸️ **Emenda (spec `device-hierarchy-capture`, 2026-08-05): para a hierarchy, o padrão desta seção foi revertido — com números, não por preferência.** Medido nesta máquina (Galaxy A07, `com.vtex.pnp`): `maestro hierarchy --no-reinstall-driver` ~3,83 s em regime; `inspect_screen` numa sessão já inicializada ~250–300 ms. A 4.3.8 nomeia ~4 s como o limiar em que a sessão persistente vale mais que a árvore crua, e 3,83 s cabe nele sem folga. Num produto cujo loop central (5.5) tem a árvore no caminho crítico, 14× decide.

Os três motivos acima continuam verdadeiros — viraram **custo**, não impedimento:

1. A perda é real e está paga no `HierarchyParser`: ele lê a tabela de abreviações e os `defaults` **da própria resposta**, e rejeita a resposta inteira em vez de devolver árvore parcial (§5.2).
2. A ausência de contrato é absorvida pelo tratamento de erro do serviço, como qualquer outra dependência externa deste app. O escopo segue mínimo: **uma** ferramenta nomeada, `inspect_screen`.
3. Segue valendo, e é por isso que `runFlow` / `checkSyntax` (§13 passo 6) continuam destinados à CLI crua.

⚠️ **E os dois não convivem.** Ainda ao escopar esta spec, uma sessão `maestro mcp` viva foi corrida contra três `maestro hierarchy` concorrentes: nenhum dos três errou ou deu timeout, mas as contagens de linha vieram 2534, 1502 e 1982 contra uma baseline limpa de 2677 em seis chamadas repetidas. O modo de falha é **pior** que o que a 4.3.6 previa ("timeout, sessão derrubada, hierarchy vazia"): dado silenciosamente incompleto, reportado como sucesso. Quem for escrever o `CliRunner` não pode assumir que um `maestro mcp` nosso e um `maestro` cru são seguros em paralelo só porque nenhum dos dois quebra.

#### 4.3.3 Por que a IA usa o MCP

1. **Apaga trabalho nosso.** Sem isso, precisaríamos construir um MCP server próprio só para dar visão de device ao Claude Code.
2. **⭐ `cheat_sheet` elimina uma armadilha silenciosa.** A alternativa era mantermos um `maestro-cheatsheet.md` à mão, com revisão a cada upgrade da CLI — e o modo de falha é a IA gerar sintaxe obsoleta **sem avisar**. A ferramenta vem da CLI instalada: sempre em sincronia, zero manutenção.
3. **Sessão persistente.** Verificado no `McpMaestroSessionManager`: o servidor roda **dentro da JVM** e mantém a sessão de device viva. O `inspect_screen` é uma chamada num objeto em memória — não paga o cold start que a 4.4 identifica como custo central. É também o **único** caminho hoje para uma sessão Maestro persistente, já que o Studio saiu do open-source (4.5).

#### 4.3.4 ⚠️ As ferramentas de Cloud vêm juntas — allowlist obrigatória

Verificado em `McpServer.kt`: o `addTools` registra as dez ferramentas **incondicionalmente**. Não há flag para excluir as de Cloud:

```
locais:  list_devices · take_screenshot · run · inspect_screen · cheat_sheet
viewer:  open_maestro_viewer
cloud:   list_cloud_devices · run_on_cloud · get_cloud_run_status · describe_cloud_run
```

Pior: o servidor envia ao modelo um bloco `INSTRUCTIONS` que **ensina ativamente o fluxo de Cloud**, incluindo `maestro login` e `MAESTRO_CLOUD_API_KEY`.

Elas não disparam sozinhas, mas ficam **anunciadas ao modelo**. Num app corporativo da VTEX, "o modelo decidiu subir o flow para a Maestro Cloud" não é algo a deixar por conta da sorte. Sem `maestro login` a chamada falha — então o pior caso é um turno perdido com erro confuso, não upload silencioso. Ainda assim, é evitável de graça.

🔷 **Allowlist no cliente, nunca blocklist:**

```
--allowedTools "mcp__maestro__inspect_screen,mcp__maestro__take_screenshot,\
mcp__maestro__list_devices,mcp__maestro__cheat_sheet,Read,Edit,Write,Glob,Grep"
```

Mesmo princípio da regra de lint em 10.1: se o Maestro adicionar ferramentas de Cloud num upgrade, elas ficam de fora **automaticamente**. Uma blocklist envelheceria em silêncio.

⚠️ **Confirmar o formato exato do nome** (`mcp__<server>__<tool>`) na primeira execução. É a convenção do Claude Code, mas vale ler o nome que ele reporta antes de fixar a lista.

⚠️ **O bloqueio acontece no cliente, antes de o modelo saber que a ferramenta existe** — não no servidor. É o Claude Code que decide o que expor.

#### 4.3.5 As outras superfícies de rede do `maestro mcp`

O transporte é **STDIO puro** (`StdioServerTransport` sobre stdin/stdout): não abre porta, não escuta socket. Restam três pontos, todos cobertos:

| Superfície | Cobertura |
|---|---|
| Telemetria PostHog | O código do MCP menciona "first-run analytics notice" — a maquinaria está no caminho. Coberto por `MAESTRO_CLI_NO_ANALYTICS=1` |
| Viewer HTTP | Só `127.0.0.1`, e some por completo com **`--no-viewer`** |
| `https://docs.maestro.dev/llms.txt` | Sugerido ao modelo no `INSTRUCTIONS`. Coberto por não habilitarmos `WebFetch` (6.0) |

Com allowlist + `--no-viewer` + a env var, o processo fica genuinamente offline.

⚠️ **Emenda (spec `device-identity-and-viewer`): existem dois `maestro mcp`, e só um deles é offline.** O da IA continua exatamente como acima. O do Conductor — o que o `ViewerService` sobe para o inspetor de device — **consome** o Viewer HTTP em vez de fechá-lo: é o único caminho suportado para chegar à URL, já que o transporte é STDIO puro e a porta não é documentada. Ele **não** leva `--no-viewer`, e o Viewer abre no navegador do usuário, servido em `127.0.0.1` pela própria JVM do Maestro. Continua sem credencial, sem rede externa e sem backend nosso, mas a afirmação "genuinamente offline" **não vale para esse filho**. `MAESTRO_CLI_NO_ANALYTICS=1` e a ausência de `WebFetch` seguem valendo para os dois.

⏸️ **Emenda (spec `device-hierarchy-capture`, 2026-08-05): a ressalva acima caiu — os dois voltaram a ser offline.** O filho do Conductor não abre mais Viewer nenhum: o `ViewerService` virou `MaestroMcpService`, chama `inspect_screen` no lugar de `open_maestro_viewer`, e leva `--no-viewer` como o da IA. Não há mais servidor HTTP em `127.0.0.1`, nem navegador, nem URL. "Genuinamente offline" volta a valer para os dois filhos, sem ressalva.

#### 4.3.6 ⚠️ Risco a verificar no spike: contenção de device

Dois processos Maestro na mesma máquina — o MCP segurando sessão viva e a nossa CLI abrindo outra para `hierarchy` — disputam o **mesmo driver on-device** (servidor gRPC no Android, XCUITest no iOS).

**Não sabemos se coexistem.** É o tipo de coisa que falha de forma confusa: timeout, sessão derrubada, hierarchy vazia. **Se conflitarem, o híbrido não fecha** e a decisão vira fonte única para tudo — provavelmente o MCP, aceitando o formato lossy e compensando com heurística no hit-test.

Entra na lista do spike (seção 13, passo 1).

#### 4.3.7 Desenho

Toda a aplicação conversa com **uma única interface, `MaestroGateway`**. Nada de `spawn` espalhado pelo código.

```ts
interface MaestroGateway {
  listDevices(): Promise<Device[]>;
  hierarchy(deviceId: string): Promise<TreeNode>;   // maestro hierarchy cru
  screenshot(deviceId: string): Promise<Buffer>;    // via SO — ver 4.4
  runFlow(path: string, opts): AsyncIterable<RunEvent>;
  checkSyntax(path: string): Promise<SyntaxResult>;
  startDevice(opts): Promise<Device>;
}
```

Uma única implementação (`LocalGateway`), mas a interface permanece porque é o ponto de troca caso a execução vá para remoto (10.1).

O Gateway cresce por spec: a primeira implementada (`device-identity-and-viewer`) trouxe só as capacidades de device — `listDevices`, `deviceProperties(deviceId)` e `appIdentity(deviceId, appId)`, todas via `AdbBridge`. As demais entram com a spec que precisar delas.

⚠️ **O `maestro mcp` fica fora do `MaestroGateway` — e agora existem dois deles.**

1. **O da IA.** Não é consumido por nós: é um subprocesso que o **Claude Code** gerencia, configurado por nós via `--mcp-config`. Quem cuida do ciclo de vida dele é o `AIService` (9.2). Inalterado.
2. **O nosso** (emenda da spec `device-identity-and-viewer`, revista pela `device-hierarchy-capture`). O Conductor sobe um `maestro mcp` próprio, fala JSON-RPC no stdio dele por um `McpClient` nosso e chama **uma** ferramenta: hoje `inspect_screen`, para ler a hierarchy. Um único filho por sessão — o cold start da JVM se paga uma vez, não a cada chamada: medido nesta máquina, 5.959 ms a frio contra 298 ms a quente. Dono do ciclo de vida é o `MaestroMcpService`, que implementa `dispose()` e é morto no `before-quit`.
   ⏸️ **O que mudou:** a ferramenta era `open_maestro_viewer` e o serviço se chamava `ViewerService`. Ele também ficava **fora** do Gateway, "pela mesma razão que o outro: não é uma chamada ao Maestro para obter dados de teste". Agora é exatamente isso, então o `LocalGateway` passou a chamá-lo (§12.9). O ciclo de vida próprio continua e continua morando no `index.ts` — o Gateway recebe o serviço por injeção e chama um método, sem saber que há um filho atrás.

⚠️ Isso torna o risco de **contenção de device da 4.3.6 realmente exercitável**: com o nosso `mcp` vivo e uma chamada `maestro hierarchy` em paralelo, os dois disputam o mesmo driver on-device. Deixou de ser item de spike e virou checagem de release.

#### 4.3.8 Gatilho para revisar

Se o spike (13.1) mostrar `maestro hierarchy` acima de **~4s** mesmo com `--no-reinstall-driver`, a sessão persistente passa a valer mais que a árvore crua, e a UI migra para o MCP também. Decisão com número na mão, não por intuição.

### 4.4 Performance — o problema real a resolver ⚠️

Sem processo persistente, **cada chamada paga cold start da JVM**. É o custo central desta arquitetura, e há três alavancas verificadas no código-fonte que o tornam gerenciável.

#### (a) ⭐ `--no-reinstall-driver` — a maior economia

Verificado em `PrintHierarchyCommand.kt` e `TestCommand.kt`: a flag `--reinstall-driver` tem **`defaultValue = "true"`**. Ou seja, **por padrão, cada `maestro hierarchy` reinstala o driver** — no iOS o xctestrunner, no Android o driver *e* o server app.

⚠️ **Isso custa dezenas de segundos e é a causa número um de lentidão.** A flag é `negatable`:

```bash
maestro hierarchy --no-reinstall-driver
```

**Regra:** o Conductor reinstala o driver **uma vez**, ao conectar o device, e usa `--no-reinstall-driver` em **todas** as chamadas seguintes. Reinstalação vira ação explícita de recuperação ("Reconectar device"), nunca rotina.

#### (b) ⭐ Screenshot não precisa passar pelo Maestro

Descoberta que melhora bastante a UX: o screenshot pode vir **direto do SO**, sem JVM.

| Plataforma | Comando | Latência |
|---|---|---|
| Android | `adb exec-out screencap -p` | **~857 ms medido** (estimativa antiga: ~100–300 ms) |
| iOS (simulador) | `xcrun simctl io booted screenshot --type=png -` | ~200–400 ms (ainda estimado) |

Ambos escrevem PNG em stdout. Isso permite **duas cadências independentes** (detalhe em 5.5): mirror visual fluido e barato, inspeção estrutural sob demanda e cara.

⏸️ **Medido em hardware, 2026-08-04** (Galaxy A07 / `SM-A075M`, Android 16, USB) — este é o passo 1 da seção 13, que até aqui nunca tinha sido rodado:

| O quê | Medido |
|---|---|
| `adb exec-out screencap -p`, 5 execuções | 834, 856, 857, 883, 882 ms → **teto de ~1,2 fps** |
| Mirror scrcpy, quadros decodificados | 85 pacotes / 370 KB em 2,8 s → **30,9 fps** |
| `mirror:start` até o codec header | 559–873 ms (quase tudo é o `app_process` subindo) |
| Encoder do device | **H.264 High profile, nível 3.2** (`avc1.640020`) |

⚠️ **O `screencap` é ~3x pior do que a estimativa que estava aqui.** A cadência rápida documentada não daria 2–4 fps neste aparelho: daria **1,2**. A decisão de trocar por scrcpy foi tomada contra o número estimado e o número real a reforça.

⚠️ **O encoder é High profile, não baseline.** Um `avc1.42E01E` hardcodado — o valor que quase todo exemplo de WebCodecs usa — estaria errado exatamente no aparelho contra o qual isto foi verificado. É por isso que a string do codec sai do SPS.

**Ainda não medido:** latência glass-to-glass (precisa de câmera filmando device e tela juntos). O que está acima é cadência de quadro e tempo de partida, não o atraso ponta a ponta que a 4.3.8 usa como gatilho.

#### (c) Telemetria — desligar

⚠️ A CLI do Maestro envia analytics para **PostHog** (`Analytics.trackEvent(...)` em cada comando). Opt-out verificado em `Analytics.kt`:

```
MAESTRO_CLI_NO_ANALYTICS=1
```

🔷 O Conductor deve injetar essa variável em **todo** subprocesso que criar. Além de evitar latência de rede no encerramento (`Analytics.flush()`), é o comportamento correto para uma ferramenta corporativa — não é decisão nossa exportar dados de uso da VTEX.

#### (d) Otimização futura, com ressalva ❓

Existe um caminho para latência de milissegundos: falar **direto com o driver on-device** — servidor gRPC no Android (o Maestro forwarda a porta via `adb forward`), servidor HTTP do XCUITest no iOS. As opções globais `--host` / `--port` / `--driver-host-port` da CLI confirmam que o driver é um serviço separado e endereçável.

⚠️ **Não fazer isso agora.** É protocolo interno, sem contrato público, e viola o princípio da fonte única (seção 5.1) — se nossa leitura divergir da do Maestro, voltamos exatamente ao bug que a arquitetura inteira existe para evitar. Registrado apenas como possibilidade caso a latência se prove intolerável na prática, e nesse caso **medindo antes**.

### 4.5 ⚠️ Sobre o Maestro Studio: não dependa dele

O módulo `maestro-studio` **foi removido do repositório open-source** do Maestro (verificado: a árvore atual de `mobile-dev-inc/Maestro` não contém mais esse módulo; o que existe é `maestro-cli/src/main/java/maestro/cli/mcp/`).

**Consequências:**
- ❌ Não construir nada sobre a API HTTP não-documentada do Studio em `localhost:9999`. Ela não tem contrato público e pode desaparecer.
- ✅ O caminho da **UI** é a CLI, encapsulada no `MaestroGateway` (4.3). A CLI é a superfície mais estável que o Maestro oferece — é o contrato público da ferramenta.
- ⚠️ O `maestro mcp` herda parte desse risco: também não é API versionada. É por isso que ele fica restrito à camada de IA (4.3.2) — ali uma quebra custa uma feature, não o produto.
- O "Maestro Viewer" (device embarcado, introduzido na v2.6.0) é servido por um servidor Ktor local que delega o streaming a um binário `simulator-server`, com eventos via SSE. É **detalhe interno da implementação** deles. Desligamos com `--no-viewer` (4.3.5). Podemos nos inspirar na abordagem; não devemos acoplar a ela.

## 5. Captura de elemento — a discussão que você pediu

> Você propôs Accessibility Tree e pediu que eu apontasse se há caminho melhor. Aqui está.

### 5.1 Veredito: a intuição está certa, o alvo precisa de um ajuste

Accessibility Tree é a **fonte subjacente correta** — mas o que o Conductor deve consumir não é "a accessibility tree do sistema operacional". É a **View Hierarchy do Maestro**, que é o que o Maestro derivou daquela árvore.

A distinção não é acadêmica. É o ponto mais importante deste documento:

> **O Conductor deve enxergar exatamente aquilo que o Maestro enxerga — nem mais, nem menos.**

Se o Conductor inspecionar a tela por qualquer outro caminho, ele vai gerar seletores que parecem corretos na nossa UI e **falham no `maestro test`**. Para o público não-técnico, esse é o pior modo de falha possível: o teste foi montado clicando na tela, e mesmo assim não roda. Usar a mesma fonte de verdade elimina essa classe inteira de bug **por construção**, não por esforço de QA.

Como o Maestro monta essa árvore:

| Plataforma | Origem real dos dados |
|---|---|
| **Android** | Servidor gRPC on-device (baseado em UIAutomator, que lê a árvore de acessibilidade) |
| **iOS** | Runner XCUITest (`maestro-ios-xctest-runner`) |

Ou seja: accessibility tree **é** o substrato — mas normalizado, filtrado e anotado pelo Maestro. Consumimos o produto final, não a matéria-prima.

### 5.2 Formato da árvore — o que consumimos (verificado no código-fonte)

**Usamos o formato cru de `maestro hierarchy`** (sem `--compact`). Ele serializa a classe `TreeNode` diretamente com Jackson, `NON_NULL` + pretty printer. Sem filtragem, sem abreviação:

```json
{
  "attributes": {
    "bounds": "[0,0][1080,2340]",
    "resource-id": "com.vtex.pnp:id/login_button",
    "text": "Entrar",
    "content-desc": "Botão de login",
    "hintText": "",
    "class": "android.widget.Button",
    "scrollable": "false"
  },
  "children": [ /* … TreeNode[] recursivo … */ ],
  "clickable": true,
  "enabled": true
}
```

Atributos por plataforma:

| Atributo | Android | iOS |
|---|---|---|
| `bounds` | ✅ | ✅ |
| `text` | ✅ | ✅ |
| `resource-id` | ✅ | ✅ |
| `content-desc` | ✅ | — |
| `accessibilityText` | — | ✅ |
| `hintText` | ✅ | ✅ |
| `class` | ✅ | — |
| `value` | — | ✅ |
| `scrollable` | ✅ | — |

⚠️ **Booleanos aparecem em dois lugares e não são equivalentes.** `clickable`, `enabled`, `focused`, `checked`, `selected` existem tanto como **campos de topo do `TreeNode`** (`boolean | null`) quanto, às vezes, dentro de `attributes` **como string** (`"true"` / `"false"`).

O próprio código do Maestro lê os **campos de topo** — nosso parser deve fazer o mesmo, e tratar `null` como "não informado", não como `false`.

Formato de `bounds`: `[x1,y1][x2,y2]`.

⚠️ **Unidade de `bounds` difere por plataforma.** Android (UIAutomator) reporta em **pixels físicos**. iOS (XCUITest) reporta em **pontos lógicos** — em tela Retina, 2× ou 3× menor que o screenshot. Ignorar isso quebra o hit-test em silêncio: no iOS o mouse acerta um elemento e o Conductor seleciona outro.

🔷 **Correção robusta — calibrar, não adivinhar.** Em vez de hardcodar fatores por device, derive a escala comparando a largura do nó raiz da hierarchy com a largura em pixels do screenshot:

```ts
const scale = screenshotWidthPx / rootNodeBoundsWidth;
```

Funciona em qualquer device, em ambas as plataformas, sem tabela de modelos para manter.

⚠️ **Emenda (spec `device-hierarchy-capture`, 2026-08-05): o nó raiz pode não ter `bounds` nenhum, e nesta máquina não tem.** Confirmado no hardware (Galaxy A07 `R9QYC01EMXL`), não inferido: a raiz que o `inspect_screen` devolve vem sem o campo, e a fórmula acima divide por `null`. A âncora existe um nível abaixo — o segundo filho da raiz reporta `[0,0][720,1600]`, batendo exatamente com o screenshot de 720×1600. Quem implementar a calibração (§13 passo 4) tem que **procurar o nó mais largo que tenha `bounds`** em vez de assumir que a raiz os carrega.

#### Sobre a filtragem que o Maestro aplica no formato compacto

O `--compact` (e o `inspect_screen` do MCP) descartam nós de tamanho zero e containers vazios, e abreviam chaves (`b`, `txt`, `rid`, `a11y`, `hint`, `cls`, `val`, `scroll`, `c`).

⏸️ **Emenda (spec `device-hierarchy-capture`, 2026-08-05): passamos a consumir exatamente esse formato.** O parágrafo abaixo dizia o contrário e foi escrito antes de haver números. Medido nesta máquina (Galaxy A07, `com.vtex.pnp`): `maestro hierarchy --no-reinstall-driver` custa ~3,83 s em regime (5 chamadas, 3,74–3,96 s); `inspect_screen` numa sessão `maestro mcp` já inicializada custa ~250–300 ms — ~14×, e confirmado depois na verificação end-to-end (5.959 ms a frio, 298 ms a quente, 110 nós nos dois). O 4.3.8 nomeia ~4 s como o limiar em que a sessão persistente passa a valer mais que a árvore crua; 3,83 s cabe na margem sem folga nenhuma. O custo é real e está pago no `HierarchyParser`: o formato é lossy e abreviado, então o parser lê a tabela `ui_schema.abbreviations` **da própria resposta** em vez de uma cópia da tabela de hoje, resolve campo ausente pelo `ui_schema.defaults` **que o servidor declarou** em vez de assumir `false`/`""`, e rejeita a resposta inteira quando ela não tem a forma documentada — nunca uma árvore parcial. Continua valendo o que vem abaixo: guardamos a árvore como ela chegou e compactamos na saída.

**Consumimos esse formato** (ver emenda acima), e replicamos a lógica em dois pontos:

- **Hit-test:** ignorar nós de largura ou altura zero — são invisíveis e nunca devem ser alvo de hover.
- **Contexto da IA:** ao enviar a árvore para o modelo (seção 6.1), aplicar a mesma compactação. Reduz tokens drasticamente e é comprovadamente digerível por LLM.

Ou seja: **guardamos a árvore como ela chegou e compactamos na saída**, conforme o consumidor.

⏸️ Este parágrafo dizia "guardamos a árvore **completa**" e contrastava com o MCP, "que compacta na origem e perde a informação para sempre". A perda é real e agora é nossa — foi ela que a emenda acima aceitou em troca dos ~14×. O que continua valendo é a segunda metade: a compactação **para a IA** (6.1) é nossa e sai da árvore que guardamos, não uma segunda chamada ao servidor.

### 5.3 ⚠️ Armadilha crítica: chaves da árvore ≠ chaves de seletor

**Os nomes de atributo da árvore NÃO são chaves válidas de seletor do Maestro.** É a fonte mais comum de erro — a ponto de o Maestro alertar sobre isso na descrição da própria ferramenta `inspect_screen`.

Seletores válidos: `text`, `id`, `index`, `point`, e os relacionais (`below`, `above`, `leftOf`, `rightOf`).

Tradução obrigatória:

| Atributo na árvore | Vira, no seletor |
|---|---|
| `resource-id` | `id:` |
| `content-desc` (Android) | **`text:`** |
| `accessibilityText` (iOS) | **`text:`** — nunca `accessibilityText:` |
| `text` | `text:` |
| `class`, `hintText`, `value`, `scrollable` | ❌ **não existem como seletor.** Servem para desambiguar e exibir, nunca para selecionar. |

⚠️ **`text:` é regex full-string com IGNORE_CASE.** Match parcial **não** funciona. `text: "RNR 352"` **não** encontra um elemento cujo texto real é `"RNR 352 - Expo Launch with Cedric van Putten"`. É preciso a string inteira ou uma âncora explícita: `text: "RNR 352.*"`.

⚠️ **Sempre copiar `txt` literalmente da árvore.** Nunca derivar texto de screenshot. Um botão com ícone de coração *parece* "Favorite" numa imagem, mas pode não ter texto algum na hierarquia. Esta é a origem clássica de seletor alucinado — e vale tanto para a IA quanto para heurísticas nossas.

⚠️ **Escapar regex.** Caracteres como `$`, `[`, `(`, `.`, `+`, `?`, `*` presentes no texto precisam de escape na hora de virar seletor. `"Total: R$ 10,00"` sem escape vira um regex que não casa.

Toda essa tradução deve morar em **um único módulo bem testado** (`src/main/maestro/selector-synthesis.ts`). É a peça de maior densidade de armadilhas do projeto e a que mais merece testes unitários.

### 5.4 Estratégia de síntese de seletor 🔷

Ao passar o mouse e clicar num elemento, o Conductor escolhe o seletor nesta ordem, **subindo de nível apenas quando o nível anterior não é único na tela**:

1. **`id:`** — a partir de `rid`, quando ele veio de um `testID` de RN. Melhor caso: estável, cross-platform, imune a mudança de texto e a tradução.
2. **`text:`** — a partir de `txt` ou `a11y`, string completa e escapada, quando única.
3. **`text:` + `index:`** — quando há duplicatas legítimas (ex.: item de lista).
4. **Relacional** — `below:` / `rightOf:` ancorado num vizinho estável. Útil em listas e cards.
5. **`point:`** — último recurso. ⚠️ Frágil: quebra com qualquer mudança de layout ou resolução. Se cair aqui, a UI **deve avisar o usuário** de que o teste é frágil.

🔷 **Validação antes de escrever no YAML — inegociável.** Todo seletor sintetizado é executado contra o snapshot em memória e conta quantos nós casam:

- `0 nós` → bug na síntese. Não escrever; logar.
- `1 nó` → ✅ escrever.
- `>1 nós` → sobe para o próximo nível da estratégia.

Isso garante unicidade **antes** que o usuário descubra na execução.

🔷 **Sinalizar ausência de `testID`.** Quando um elemento não tem `testID`, o Conductor cai para `text:`, que é mais frágil. Vale registrar esses casos e oferecer um relatório — é um insumo acionável para o time do app melhorar a testabilidade, e um subproduto valioso da ferramenta.

### 5.5 Modelo de interação: duas cadências 🔷

**Problema:** consultar a hierarchy a cada movimento do mouse é impossível — cada `maestro hierarchy` custa segundos (JVM).

**Insight que resolve (seção 4.4b):** screenshot e hierarchy têm custos **muito diferentes** — ~200 ms via SO contra segundos via JVM. Tratá-los na mesma cadência desperdiça a parte barata. Então rodam em duas velocidades:

| Cadência | O quê | Como | Serve para |
|---|---|---|---|
| **Rápida — Android** (~30 fps, ~50–100 ms) | Vídeo H.264 | `scrcpy-server` (jar nosso, pinado) sobre `adb`, decodificado no renderer com WebCodecs | Mirror ao vivo **dentro do painel** — o usuário vê o app responder enquanto escreve o teste |
| **Rápida — iOS, e captura avulsa** (~1–2 fps) | Screenshot | `adb exec-out screencap` / `simctl io screenshot` | Caminho do iOS, e a imagem congelada que entra no snapshot |
| **Lenta** (sob demanda) | Hierarchy | `maestro hierarchy --no-reinstall-driver` | Inspeção, hover, síntese de seletor |

⏸️ **Emenda (spec `android-device-mirror`, 2026-08-04):** no Android a cadência rápida deixou de ser `screencap` em polling. O motivo é medido, não estético: `adb exec-out screencap -p` custa 100–300 ms por quadro, o que trava a cadência rápida em 2–4 fps — o bastante para ver *que* a tela mudou, não para ver o app responder. O `scrcpy-server` entrega ~30 fps pelo mesmo socket `adb` que já existe, sem JVM, e o canal de controle dele é o próximo passo natural.

O custo está registrado: é protocolo interno, versionado, sem contrato de estabilidade — a mesma classe de risco que 4.5 alerta. **Pinar o nosso próprio jar é o que converte esse risco de "quebra na máquina de alguém" para "quebra quando decidirmos atualizar"**, e é por isso que 4.5 veta raspar o log do Maestro mas não veta isto. `screencap` continua sendo o caminho do iOS e da captura congelada — 4.4b segue valendo inteiro.

**Snapshot** = `{ screenshot, hierarchy, scale, deviceInfo }` capturados juntos e congelados. O hover faz **hit-test 100% local** contra a árvore em memória — latência zero, sem I/O.

⚠️ **O mirror rápido pode ficar à frente do snapshot.** Se o usuário navega no app, a imagem atualiza mas a árvore não — o hover passa a apontar para elementos que já saíram da tela. **A UI precisa mostrar isso**, não esconder: quando o screenshot atual difere visivelmente do screenshot do snapshot, marcar o overlay de inspeção como desatualizado e oferecer "Atualizar". Silenciar essa divergência gera seletor errado com aparência de certo.

Recapturar o snapshot quando: o usuário pede, um comando é executado, ou o flow termina.

**Hit-test:**
1. Converter a coordenada do mouse para o espaço de `bounds` usando o `scale` calibrado (seção 5.2) — **não** o device pixel ratio do browser.
2. Descartar nós de largura ou altura zero.
3. Selecionar o nó **mais profundo e de menor área** cujos `bounds` contêm o ponto.
4. Empate: preferir `clickable === true`, depois o que tiver `resource-id`, depois `text`.
5. `Alt`/`Option` sobe para o nó pai — útil quando o alvo real é o container.

### 5.6 Alternativas avaliadas e descartadas

| Alternativa | Veredito | Por quê |
|---|---|---|
| **React Native DevTools / Hermes CDP** (árvore de componentes JS) | ❌ como fonte de seletor · 🔷 como enriquecimento visual | Dá nomes de componente e props — semanticamente mais rico. Mas **não corresponde aos seletores do Maestro**, e exige dev build com Hermes debugger. Usar só para *exibir* `Button (PDPAddToCartButton)` no lugar de `android.widget.ViewGroup`. **Jamais para gerar seletor.** |
| **Appium / appium-inspector** | ❌ | Outro driver, outra árvore. O teste roda no Maestro — divergência garantida entre o que se inspeciona e o que se executa. |
| **OCR / visão computacional sobre o screenshot** | ❌ | Produz `point:` frágil e texto alucinado. A própria documentação do Maestro alerta contra derivar texto de imagem. |
| **Instrumentar o app RN com agente próprio** | ❌ | Exigiria mudança no app da VTEX e quebraria a garantia de "zero instrumentação" do Maestro. Custo alto, benefício baixo. |
| **`adb shell uiautomator dump` / `idb` direto** | ❌ | Reimplementar o que o Maestro já faz, com risco de divergir dele. Sem ganho. |

**Resumo:** manter uma única fonte de verdade — a view hierarchy do Maestro — e opcionalmente *decorar* a apresentação com dados do RN. Nunca decidir seletor a partir da decoração.

## 6. Janela de IA ✅

Diferencial central em relação ao Maestro Studio: um assistente que **edita o `.yml` em tempo real** enquanto conversa com o usuário.

### 6.0 Motor: o Claude Code CLI da máquina do usuário ✅

**Não chamamos API de modelo. Orquestramos o `claude` (Claude Code CLI) já instalado na máquina do usuário**, em modo headless.

Mesmo padrão do `gh` (8.1) e do `maestro` (4.3): capacidade e credencial vêm da máquina. E aqui o ganho é maior que nos outros dois — ver 6.5.

**Modelo: sempre Sonnet. O usuário não escolhe** — não precisa de mais que isso para escrever teste e2e, e uma escolha a menos é uma barreira a menos (seção 1.1).

```ts
// src/shared/config.ts
AI_MODEL: process.env.CONDUCTOR_AI_MODEL ?? 'sonnet',
```

🔷 Usar o **alias `sonnet`**, não o ID fixo `claude-sonnet-5`. O alias sempre aponta para o Sonnet mais recente, sem precisarmos publicar versão do Conductor a cada modelo novo. O custo é que o comportamento pode mudar sob nós — aceitável aqui, e a env var permite pinar um ID exato se algum dia for preciso.

#### Invocação

```bash
claude -p "<prompt>" \
  --model sonnet \
  --output-format stream-json \
  --include-partial-messages \
  --add-dir "<repo>/.maestro" \
  --tools "Read,Edit,Write,Glob,Grep" \
  --permission-mode acceptEdits \
  --max-budget-usd 0.50 \
  --safe-mode
```

| Flag | Por quê |
|---|---|
| `-p` | Headless — imprime e sai, em vez de abrir sessão interativa |
| `--output-format stream-json` | Saída estruturada em streaming, para a UI consumir |
| `--include-partial-messages` | Chunks parciais → texto aparecendo token a token no chat |
| `--input-format stream-json` | Turnos múltiplos num processo só — evita respawn a cada mensagem |
| `--session-id <uuid>` / `--resume` | Alternativa ao anterior: continuidade por sessão persistida |
| `--add-dir` | Escopo de acesso a arquivo |
| `--tools` | Restringe o conjunto de ferramentas nativas |
| `--permission-mode` | Ver o alerta abaixo |
| `--max-budget-usd` | Teto de gasto por conversa |
| `--mcp-config` / `--strict-mcp-config` | Ver 6.2 |
| `--safe-mode` | Ver o alerta abaixo |

#### ⚠️ Isolar do ambiente do usuário — `--safe-mode`

Por padrão, o `claude` carrega **CLAUDE.md, skills, plugins, hooks, MCP servers, comandos e agentes customizados** do usuário. Dentro do Conductor isso é imprevisível: o CLAUDE.md pessoal de alguém pode instruir o modelo a fazer algo que não tem nada a ver com escrever flow do Maestro, e hooks de terceiros passam a rodar dentro do nosso app.

🔷 Rodar com **`--safe-mode`** (desliga todas as customizações; auth, modelo, ferramentas nativas e permissões seguem funcionando) ou, para controle mais fino, `--setting-sources` + `--strict-mcp-config`. O Conductor precisa de um ambiente **reprodutível** — se o assistente se comporta diferente na máquina de cada pessoa, é impossível dar suporte.

#### ⚠️ Headless não tem quem responder prompt de permissão

Não existe usuário para clicar "permitir" num processo `-p`. Uma ferramenta que precise de permissão e não a tenha **trava ou falha**. Toda autorização precisa ser dada **antecipadamente** via `--tools` / `--allowedTools` / `--permission-mode`.

🔷 Conjunto mínimo: `Read,Edit,Write,Glob,Grep` — **sem `Bash`**. O assistente escreve YAML; não tem por que executar shell. Somado ao `--add-dir` restrito a `.maestro/`, o raio de ação fica contido nos arquivos de teste.

### 6.1 Contexto que o modelo recebe

- **O próprio arquivo `.yml`** — ele está em disco, no clone local, e o Claude Code lê com `Read`. Não precisamos serializá-lo no prompt.
- Snapshot corrente — ver 6.2.
- Instruções do Conductor via `--system-prompt` / `--append-system-prompt`: as regras da seção 5.3 (tradução de atributos, regex full-string, escapar), o `appId` fixo, e as convenções do repositório.
- Referência de sintaxe do Maestro — ✅ **via `cheat_sheet` do MCP** (4.3.3), não um arquivo mantido por nós. Sai sempre em sincronia com a CLI instalada. A alternativa que isso substitui era um `maestro-cheatsheet.md` versionado à mão, cujo modo de falha é a IA gerar sintaxe obsoleta **em silêncio**.
- Flows já existentes no repositório — o modelo os alcança sozinho com `Glob`/`Grep`, sem custo de prompt.

### 6.2 Como a IA edita o arquivo e enxerga a tela

#### Edição: nativa, via filesystem ⭐

O requisito original — *"ela vai modificando o arquivo `.yml` em tempo real"* — cai fora quase de graça:

```
Claude Code edita o .yml  →  chokidar detecta (§7)  →  UI re-renderiza
```

O Claude Code **já sabe editar arquivo** (`Edit`, `Write`). O flow está em disco, no clone local. Não precisamos inventar ferramentas `insert_command` / `replace_command` — a edição cirúrgica é o que o `Edit` faz nativamente, e o watcher que já está na arquitetura fecha o loop.

⚠️ **Isso torna a preservação de formatação (6.3) mais crítica, não menos.** O modelo edita o arquivo direto, sem passar pelo nosso parser YAML. As regras de estilo têm que estar no system prompt, e o diff no PRPanel é a rede de proteção final.

#### Visão do device: o `maestro mcp` ✅

O Claude Code não enxerga o emulador. **Plugamos o MCP do Maestro nele** — a decisão está em 4.3, com o critério em 4.3.1 e as travas em 4.3.4/4.3.5:

```jsonc
--mcp-config '{"maestro":{"command":"maestro","args":["mcp","--no-viewer"]}}'
--strict-mcp-config   // ignora MCP servers configurados pelo usuário
```

Isso substitui a ideia anterior de construirmos um MCP server próprio. Não precisamos: as ferramentas locais do Maestro (`inspect_screen`, `take_screenshot`, `list_devices`, `cheat_sheet`) cobrem o que a IA precisa, e vêm com sessão persistente de graça.

⚠️ **`--strict-mcp-config` junto com `--safe-mode`.** Sem ele, MCP servers que o usuário configurou para uso pessoal entram na sessão do Conductor — mesma classe de imprevisibilidade que o `--safe-mode` resolve para CLAUDE.md e hooks.

⚠️ **A IA está sujeita às mesmas regras da seção 5.3.** Todo seletor que ela escrever passa pelo **mesmo validador de unicidade** da UI. Se não casa exatamente 1 nó, é rejeitado e devolvido com o motivo. O `inspect_screen` entrega a árvore compacta — as chaves abreviadas (`rid`, `a11y`, `txt`) **não são chaves de seletor**, e essa tradução tem que estar no system prompt.

❓ **Se o spike revelar contenção de device (4.3.6)**, esta parte muda: sem MCP, o fallback é escrever `snapshot.json` + `screenshot.png` num dir passado via `--add-dir` e deixar o modelo ler com `Read`. Funciona, mas o modelo passa a não conseguir pedir snapshot novo — fica cego para o resultado do que ele mesmo executou.

Ganhos: edições cirúrgicas (sem reescrita destrutiva), *undo* natural passo a passo, e um loop de feedback real — a IA roda, vê a falha e corrige.

⚠️ **A IA está sujeita às mesmas regras da seção 5.3.** Ela não tem passe livre para inventar seletor. Todo seletor que ela propõe passa pelo **mesmo validador de unicidade** usado pela UI. Se o seletor não casa exatamente 1 nó, ele é rejeitado e devolvido ao modelo com o motivo.

### 6.3 Preservação do arquivo ⚠️

Usar um parser YAML com **AST que preserva comentários e formatação** — `yaml` (eemeli). `js-yaml` faz round-trip destrutivo: come comentários e reordena chaves. Como estes arquivos vivem em Git e passam por code review, destruir formatação gera diffs ilegíveis e PRs impossíveis de revisar.

### 6.4 Credenciais: não existem ⭐

**Fechado — e melhor do que o previsto: o Conductor não lida com credencial de IA nenhuma.**

O `claude` já está autenticado na máquina, com a assinatura Claude ou a chave de API do próprio usuário. Nós invocamos o binário; a autenticação é problema dele.

O que **deixa de existir** por causa disso:

- ❌ Chave de API no keychain
- ❌ `safeStorage`, rotação, expiração
- ❌ Superfície de vazamento em log ou crash report
- ❌ Risco de embarcar chave no bundle — o erro grave que a versão anterior desta seção precisava alertar. Agora ele é **impossível por construção**: não há chave para embarcar.
- ❌ Onboarding pedindo chave de API a um usuário não-técnico

E o custo vai para a assinatura de quem usa, sem nenhum repasse ou billing intermediado por nós.

🔷 **`--max-budget-usd` como guarda-chuva.** Mesmo sendo o gasto do usuário, um loop de agente pode consumir bem mais que o esperado. Definir um teto por conversa e mostrá-lo na UI — o usuário deve saber quanto uma sessão custou.

### 6.5 Consequência arquitetural: o princípio de 9.0 fica íntegro ⭐

A seção 9.0 abria uma exceção — *"a janela de IA precisa chamar a API do provider; não há como ter IA sem isso"*. **Essa exceção desapareceu.**

Com o `claude` como motor, o Conductor não faz **nenhuma** chamada de rede autenticada em nome do usuário. A quinta linha da tabela de 9.0 fecha o padrão:

| Em vez de | Usamos |
|---|---|
| API/servidor próprio | Nada — tudo local |
| Octokit + OAuth App | `gh` CLI da máquina |
| ~~Proxy de IA / chave no keychain~~ | **`claude` CLI da máquina** |
| Farm de devices | `adb` / `simctl` locais |

Toda credencial e toda capacidade vêm da máquina do usuário — **sem exceção**. O Conductor é, literalmente, um orquestrador de ferramentas que já estão lá.

## 7. Repositório e cache local ✅

Um único repositório canônico (`CONFIG.REPO_URL`), clonado localmente. **Iterar sobre o clone, nunca fazer requisição por arquivo.**

🔷 **Design:**

- **Local:** `app.getPath('userData')/repo` — fora do projeto do usuário, respeita as convenções de cada SO.
- **Clone:** `git clone --filter=blob:none` (*partial clone*). Preferível a `--depth 1`: rápido no primeiro clone, mas **preserva histórico** — necessário para criar branch, commitar e abrir PR sem surpresa.
- **Sincronização:** `git fetch` na abertura do app e sob demanda. Mostrar claramente ao usuário quando o cache está desatualizado em relação ao remoto.
- **Watch:** `chokidar` sobre `.maestro/`, para refletir edições externas na UI.
- **Índice:** varrer `.maestro/**/*.{yml,yaml}` e manter em memória `{ path, appId, nome, comandos, hash }`. Reindexar por evento do watcher, não por polling.

⚠️ **Nem todo `.yml` em `.maestro/` é um flow.** Podem existir `config.yaml` de workspace, subflows reutilizáveis e arquivos de dados. Classificar pela presença de um header válido com `appId` (ou lista de comandos), não pela extensão.

## 8. Abertura de Pull Request ✅

O usuário conclui o teste e publica sem sair do Conductor.

**Fluxo:**
1. Criar branch a partir de `CONFIG.REPO_BASE_BRANCH` — nome derivado do flow (`conductor/checkout-com-pix`).
2. Escrever os `.yml` alterados.
3. `maestro check-syntax` como **gate**: PR não abre com YAML inválido.
4. Commit com mensagem gerada (a IA pode redigir a partir do diff).
5. Push e abertura do PR, com descrição contendo o resumo do fluxo em linguagem natural.

### 8.1 Autenticação: `gh` CLI ✅ — decidido

**Usamos o `gh`, a CLI oficial do GitHub, aproveitando a autenticação que já existe na máquina do usuário.** Sem OAuth App, sem Octokit, sem token nosso.

Coerente com a decisão de 10.1 (local agora) e com o princípio de 9.0 (só frontend): assim como o device vem da máquina, a credencial do GitHub também vem.

⭐ **O maior ganho é o que deixa de existir:** o Conductor **não guarda token nenhum**. Some uma superfície inteira — sem keychain para o GitHub, sem refresh, sem expiração para tratar, sem OAuth App para registrar e manter, sem risco de vazar credencial em log ou crash report. O `gh` já resolveu esse problema, e melhor do que resolveríamos.

⭐ **Bônus que resolve um problema que eu não tinha endereçado:** clone de **repositório privado**. Com `gh auth setup-git`, o `gh` se registra como credential helper do git — o clone funciona sem o usuário configurar chave SSH nem token manualmente. Como o repositório da VTEX é quase certamente privado, isso deixaria de funcionar em silêncio na primeira tentativa se fôssemos por outro caminho.

**Comandos usados:**

| Comando | Uso |
|---|---|
| `gh auth status` | Verificar se há login válido — entra no doctor (seção 10) |
| `gh auth setup-git` | Registrar o `gh` como credential helper, habilitando clone privado |
| `gh repo clone <repo> <dir>` | Clone inicial autenticado |
| `gh pr create --base --head --title --body` | Abrir o PR |
| `gh pr view --json url` | Recuperar a URL para exibir ao usuário |

⚠️ **Passar `--body` por arquivo (`--body-file`) ou stdin, nunca interpolado em string de shell.** A descrição do PR é gerada pela IA e contém quebras de linha, crases e aspas. Interpolar isso num comando é injeção de shell — e aqui o conteúdo é literalmente texto gerado por modelo. Usar `execFile` com array de argumentos, jamais `exec` com string montada.

⚠️ **`gh` vira dependência obrigatória** — registrada na tabela da seção 10. O doctor precisa checar duas coisas distintas: *instalado* e *autenticado*. `gh` presente mas deslogado é o caso mais provável na prática, e a mensagem de erro tem que ser específica (`gh auth login`), não genérica.

⏸️ **Nota de rollout:** exigir `gh` reforça que os primeiros usuários serão técnicos. Consistente com 10.1 — e é o mesmo gatilho de reavaliação: quando entrar gente não-técnica, `gh` e o setup local caem juntos, e aí o Device Flow volta à mesa junto com o `RemoteGateway`.

## 9. Stack e arquitetura

### 9.0 Princípio: aplicação puramente frontend ✅

**Não existe backend. Não construímos nem operamos servidor.** O Conductor é um app Electron que orquestra ferramentas já instaladas na máquina do usuário.

Isso é uma **regra de arquitetura**, e ela decide sozinha várias escolhas abaixo:

| Em vez de | Usamos | Seção |
|---|---|---|
| API/servidor próprio | Nada — tudo local | — |
| Octokit + OAuth App | `gh` CLI da máquina | 8.1 |
| API de modelo com chave nossa | `claude` CLI da máquina | 6.0 |
| Farm de devices | `adb` / `simctl` locais | 10.1 |

O padrão é consistente e **não tem exceção**: toda credencial e toda capacidade vêm da máquina do usuário, nunca de infraestrutura nossa. Nada para provisionar, nada para operar, nada para pagar por uso, **nenhum segredo sob nossa custódia**.

⭐ Uma versão anterior desta seção abria uma exceção para a janela de IA — "não há como ter IA sem chamar a API do provider". A decisão de usar o `claude` CLI (6.0) a eliminou. Ver 6.5.

O Conductor é, com precisão literal, um **orquestrador de ferramentas que já estão na máquina**: `maestro`, `git`, `gh`, `claude`, `adb`/`simctl`. Ele não é cliente de nada remoto.

## 10. Pré-requisitos de ambiente ⚠️ — risco de produto

Esta é a maior ameaça à premissa "qualquer usuário, mesmo que não seja dev". O Maestro **não é autossuficiente**:

| Dependência | Necessária para | Problema |
|---|---|---|
| **Maestro CLI** | Tudo | Roda em JVM; precisa ser instalada |
| **JDK** | Maestro | Pode não existir na máquina |
| **Android SDK / `adb`** | Testar em Android | Instalação pesada |
| **Xcode + `simctl`** | Testar em iOS | Só macOS, download de dezenas de GB |
| **Device/emulador** | Tudo | Precisa estar rodando |
| **`gh` CLI** | Abrir PR, clonar repo privado | ⚠️ Checar **instalado _e_ autenticado** — são falhas distintas. Ver 8.1 |
| **`git`** | Repo local | Garantido de fato: `gh` depende dele |
| **`claude` CLI** | Janela de IA | ⚠️ Também **instalado _e_ autenticado** (`claude auth`). Ver 6.0. Sem ele, a IA fica indisponível — mas o resto do app funciona |

🔷 **O Conductor precisa de um "doctor" na primeira execução:** detectar cada dependência, explicar em linguagem simples o que falta, e automatizar o que der (instalação do Maestro via script oficial, `maestro start-device` para subir emulador).

### 10.1 Decisão: local agora, remoto depois ✅

**Execução local**, com o doctor guiando a instalação. **Mas registrada como temporária** — o atrito de setup continua sendo a maior ameaça à premissa "qualquer usuário, mesmo que não seja dev", e a migração para remoto é esperada, não hipotética.

```
MaestroGateway            ◄── contrato estável, agnóstico de local/remoto
  ├── LocalGateway        (hoje)   CliRunner + ScreenCapture
  └── RemoteGateway       (depois) farm de devices
```

⚠️ **Uma decisão adiada só continua barata se o acoplamento não vazar.** "Local agora" degrada para "local para sempre" quando pressupostos de localidade se espalham pelo código. As regras abaixo são o que mantém a opção aberta — cada uma é uma forma concreta de vazamento:

| # | Regra | Vazamento que ela previne |
|---|---|---|
| 1a | Só `run.ts` e `CliRunner` importam `child_process` | Criação de processo espalhada pelo código |
| 1b | Só `CliRunner`, `ScreenCapture`, `AdbBridge`, `ScrcpySource` e `MaestroMcpService` mencionam `adb`, `xcrun`, `simctl`, `maestro` ou caminhos do scrcpy | Conhecimento de "onde o device vive" espalhado pelo código |
| 2 | Screenshot atravessa a interface como **bytes** (`Buffer`), nunca como caminho de arquivo | Path local não existe no device remoto |
| 3 | `deviceId` é **token opaco** — nunca parseado nem interpretado | Hoje é serial adb/UDID; amanhã é id de sessão |
| 4 | Toda operação do Gateway é `async` e **pode falhar por rede** | API síncrona não sobrevive à rede |
| 5 | Nenhum consumidor assume latência baixa nem ordem de chegada | Loop apertado que trava com 300 ms de RTT |
| 6 | Nada fora do Gateway lê o filesystem do device | Só o Gateway sabe onde o device vive |

⏸️ **Emenda (spec `android-device-mirror`, 2026-08-04):** a regra 1 original juntava duas coisas que se separaram na prática. `AdbBridge` e `ScrcpySource` sabem o nome do `adb` e o caminho do jar no device, mas **não criam processo**: recebem o runner por injeção de construtor, e é isso que torna cada armadilha delas testável sem device nenhum. Quem cria processo continua sendo só os arquivos da regra 1a — e é só esses que o `noRestrictedImports` abaixo libera.

⏸️ **Emenda (spec `device-hierarchy-capture`, 2026-08-05): `ScreenCapture` saiu da 1a e entrou na 1b, e `MaestroMcpService` entrou na 1b.** A emenda acima estabeleceu o critério; `ScreenCapture` é o terceiro módulo a satisfazê-lo — nomeia `adb`, recebe `runBinary` por injeção e não importa `child_process`. Manter a exceção de lint num arquivo que não precisa dela é porta aberta para o próximo edit, então ela caiu e o teste de `ScreenCapture` passou a afirmar isso. Sobra `run.ts` (e `CliRunner`, quando existir). Na 1b entra `MaestroMcpService`: ele resolve o binário `maestro` — herdado do `ViewerService`, que já fazia isso — e a lista precisa nomeá-lo em vez de deixar a regra falsa por omissão.

🔷 **Tornar a regra 1a executável**, não apenas escrita. Em **Biome**, a regra é `style/noRestrictedImports`, com a exceção via `overrides`:

```jsonc
// biome.json
{
  "linter": {
    "rules": {
      "style": {
        "noRestrictedImports": {
          "level": "error",
          "options": {
            "paths": {
              "node:child_process":
                "Somente run.ts e CliRunner criam processos — os demais recebem o runner por injeção. Ver .context.md §10.1.",
              "child_process":
                "Use o especificador 'node:'. E somente em run.ts/CliRunner. Ver §10.1."
            }
          }
        }
      }
    }
  },
  "overrides": [
    {
      // Os únicos arquivos que criam processo.
      "includes": [
        "src/main/maestro/CliRunner.ts",
        "src/main/process/run.ts"
      ],
      "linter": { "rules": { "style": { "noRestrictedImports": "off" } } }
    }
  ]
}
```

⚠️ **Restringir as duas grafias.** `node:child_process` e `child_process` são especificadores distintos para o Biome; bloquear só o primeiro deixa a porta aberta.

⚠️ **`overrides` não faz deep merge de opções no Biome** — por isso a exceção **desliga** a regra nos dois arquivos, em vez de redefinir `paths`. Tentar mesclar não funciona.

Isso transforma a decisão arquitetural em erro de build. É a diferença entre uma convenção que erode em silêncio e uma que se sustenta.

⚠️ **A regra cobre `child_process`, não `gh`/`adb`/`simctl` como strings.** Um `GhService` que rode comandos precisa ele próprio criar processos — e a regra vai (corretamente) reclamar. Duas saídas: ou `GhService` entra na lista de exceções, ou — melhor — todo spawn passa por um utilitário único (`src/main/process/run.ts`), que vira o **terceiro e último** arquivo com exceção. A segunda opção também centraliza o `execFile` seguro exigido em 8.1.

🔷 **Doctor desde já.** Mesmo em modo local, ele é o esqueleto do futuro estado de conexão remota: "o que preciso para rodar, e o que está faltando" é a mesma pergunta nos dois mundos.

❓ **Gatilho para reavaliar:** quando os primeiros usuários não-técnicos entrarem. Se o setup travar o onboarding deles, é hora do `RemoteGateway` — e as regras acima é que decidem se isso custa dias ou meses.

## 11. Glossário

| Termo | Significado |
|---|---|
| **Flow** | Um teste e2e. Arquivo `.yml` em `.maestro/`. |
| **View hierarchy** | Árvore de elementos da tela, como o Maestro a enxerga. Fonte de verdade para seletores. |
| **Seletor** | Como um comando identifica um elemento (`id:`, `text:`, `index:`, relacionais, `point:`). |
| **Snapshot** | `{ screenshot + hierarchy }` capturados juntos, congelados para o hover local. |
| **`appId`** | Package name (Android) / bundle id (iOS). Sempre `CONFIG.APP_ID`. |
| **MCP** | Model Context Protocol. Ver 11.1 — usado **só na camada de IA** (4.3). |
| **`MaestroGateway`** | Interface única do Conductor para falar com o Maestro. Todo acesso passa por ela. |
| **Snapshot** vs. **mirror** | Mirror = screenshot ao vivo, barato. Snapshot = screenshot + hierarchy congelados, caro. Ver 5.5. |

### 11.1 O que é MCP, de fato

Padrão aberto (criado pela Anthropic, especificação pública) para **descrever capacidades a um modelo de IA e deixá-lo invocá-las**.

#### O problema que resolve

Um LLM sozinho só produz texto. Para ele fazer algo — ler arquivo, inspecionar device — alguém precisa **descrever** a capacidade (nome, o que faz, parâmetros), **receber** o pedido estruturado, **executar** e **devolver** o resultado.

Antes do MCP, cada aplicação fazia isso do seu jeito: 5 apps × 10 ferramentas = 50 integrações. Com protocolo comum, viram 5 + 10.

**A analogia exata é o LSP** (Language Server Protocol) — e não por acaso, foi a inspiração. Antes do LSP, cada editor implementava autocomplete para cada linguagem. Depois, cada linguagem escreve *um* server e todo editor que fala o protocolo ganha suporte. MCP é a mesma ideia para ferramentas de LLM.

#### Arquitetura

Dois papéis:

- **Cliente (host)** — a aplicação onde o modelo vive: Claude Code, Cursor, Claude Desktop
- **Servidor** — quem expõe capacidades: `maestro mcp`, um servidor de banco

Conversam por **JSON-RPC 2.0**, quase sempre sobre **STDIO**: o cliente sobe o servidor como subprocesso e troca mensagens por stdin/stdout. É por isso que o `maestro mcp` não abre porta nenhuma (4.3.5).

Um servidor expõe três primitivas. Na prática a primeira domina:

| Primitiva | O quê |
|---|---|
| **Tools** | Ações que o modelo invoca — `inspect_screen`, `run` |
| **Resources** | Dados que o modelo lê, como arquivos |
| **Prompts** | Templates que o usuário aciona |

#### O fluxo

```
1. Cliente sobe o servidor            → spawn `maestro mcp`
2. Handshake: "o que você tem?"       → servidor devolve tools + JSON Schema
3. Cliente injeta as descrições no contexto do modelo
4. Modelo decide: "preciso ver a tela" → emite tool-call estruturado
5. Cliente intercepta                  → JSON-RPC `tools/call` ao servidor
6. Servidor executa                    → fala com o device
7. Servidor devolve                    → cliente entrega ao modelo
8. Modelo continua
```

⚠️ **O modelo nunca fala com o servidor direto.** O cliente é sempre o intermediário — é ele que decide o que expor, o que bloquear e o que registrar. Por isso a allowlist de 4.3.4 funciona: ela age no cliente, antes de o modelo saber que a ferramenta existe.

#### O que MCP não é

- Não é serviço, produto ou coisa hospedada — não existe "a nuvem do MCP"
- Não é necessariamente rede: com STDIO é subprocesso local
- Não é IA — é só um jeito padronizado de descrever e chamar função

#### Aplicado ao Conductor

| Peça | Papel |
|---|---|
| `maestro mcp` | O binário `maestro` em **modo servidor**: em vez de rodar um comando e sair, fica vivo falando JSON-RPC |
| Claude Code | **Cliente** — sobe servidores e medeia |
| Conductor | **Nem um nem outro.** Configura o cliente (`--mcp-config`) e fica fora do caminho |

E o critério que organiza tudo: **MCP só compensa quando há um modelo numa das pontas** (4.3.1).

## 12. Regras para agentes de IA que trabalharem neste repositório

1. **Uma fonte de verdade para seletores:** a view hierarchy do Maestro. Nunca derivar seletor de screenshot, de OCR ou da árvore de componentes RN.
2. **Traduzir chaves antes de gerar seletor:** `rid`→`id:`, `a11y`→`text:`, `txt`→`text:`. As chaves abreviadas não são chaves de seletor.
3. **`text:` é regex full-string, case-insensitive.** String completa ou âncora `.*`. Escapar caracteres especiais.
4. **Copiar texto literalmente da árvore.** Nunca transcrever de imagem.
5. **Validar unicidade** de todo seletor contra o snapshot antes de escrever no YAML.
6. **`CONFIG.APP_ID` e `CONFIG.REPO_URL`** — nunca hardcode os valores fora de `src/shared/config.ts`.
7. **Preservar formatação do YAML.** AST com comentários. Estes arquivos passam por code review.
8. **Renderer não executa comandos.** Toda ação privilegiada mora no processo main.
9. **Toda chamada ao Maestro feita por nós passa pela interface `MaestroGateway`.** Nunca `spawn` direto espalhado pelo código. O `maestro mcp` da IA é a exceção e fica **fora** do Gateway — quem o gerencia é o Claude Code, não nós (4.3.7).
   ⏸️ **Emenda (spec `device-hierarchy-capture`, 2026-08-05):** o `maestro mcp` **nosso** deixou de ser exceção. A emenda da `device-identity-and-viewer` o punha fora do Gateway com a justificativa de que "não é uma chamada ao Maestro para obter dados de teste, é um processo com ciclo de vida próprio". A primeira metade parou de ser verdade: `hierarchy()` é exatamente uma chamada para obter dados de teste. A segunda continua, e é por isso que o dono do ciclo de vida segue sendo o `MaestroMcpService`, construído e descartado no `index.ts` — o `LocalGateway` recebe o serviço por injeção e chama um método, sem saber que existe um filho por trás.
10. **Todo processo `maestro` leva `MAESTRO_CLI_NO_ANALYTICS=1`** — inclusive o `mcp`, os dois. A flag `--no-reinstall-driver` vale só para `hierarchy` / `test` (não existe no subcomando `mcp`); exceção única, a reinstalação explícita ao conectar o device. **Os dois `mcp` levam `--no-viewer`.**
    ⏸️ **Emenda (spec `device-hierarchy-capture`, 2026-08-05):** a exceção única e nomeada que esta regra abria — "o `maestro mcp` do `ViewerService` **não** leva `--no-viewer`" — acabou junto com o `ViewerService`. Nada no app abre uma URL de Viewer, então a flag voltou a valer para os dois filhos, e a regra voltou a não ter exceção.
11. **MCP só onde há um modelo na ponta** (4.3.1) — **com uma exceção, aberta pela spec `device-identity-and-viewer` e alargada pela `device-hierarchy-capture`.** A regra segue valendo como padrão: IA consome MCP, e diante de "isso deveria ser MCP?" aplique o critério. A UI só pode agir como cliente MCP restrita a ferramentas nomeadas, uma a uma — hoje `inspect_screen`, e nada mais.
    ⏸️ **Emenda (spec `device-hierarchy-capture`, 2026-08-05):** o critério original era "a capacidade **existe exclusivamente** atrás do MCP", e o fecho desta regra dizia "Nada disso vale para dados de árvore: hit-test e síntese de seletor continuam na CLI crua, pelo motivo da 4.3.2 — o formato compacto é lossy". Ambos mudaram. A árvore **existe** na CLI crua, então o teste de exclusividade não é mais o que decide: o que decidiu foi latência medida (~3,83 s contra ~250–300 ms, §5.2), num produto cujo loop central (5.5) tem a árvore no caminho crítico. O critério passa a ser **exclusividade ou uma diferença de latência medida que atravesse o limiar da 4.3.8** — medida, nunca estimada — e a perda do formato compacto continua sendo custo real, absorvido pelo `HierarchyParser` (§5.2). O caso original permanece válido pelo motivo original: a URL do Viewer só existia atrás de `open_maestro_viewer` (ferramenta que este app não chama mais).
12. **A allowlist de ferramentas MCP é allowlist, nunca blocklist** (4.3.4). As ferramentas de Cloud vêm registradas incondicionalmente e são anunciadas ao modelo.
13. **A imagem do device vem do SO, nunca do Maestro.** Screenshot avulso é `adb exec-out screencap` / `simctl io screenshot` (4.4b); o mirror ao vivo do Android é o `scrcpy-server` sobre `adb`, com o jar pinado por nós (5.5). Nenhum dos dois passa por JVM nem pelo binário `maestro` — e nenhum lê o scrcpy instalado na máquina do usuário, porque o argumento de versão precisa bater com o jar exatamente.
14. **Escala de `bounds` é calibrada, nunca hardcodada.** iOS reporta em pontos, Android em pixels. Ver 5.2.
15. **Não existe backend.** Não criar servidor, endpoint ou serviço. Capacidade e credencial vêm da máquina do usuário. Ver 9.0.
16. **GitHub é sempre via `gh`.** Sem Octokit, sem OAuth, sem token guardado por nós. Ver 8.1.
17. **IA é sempre via `claude` CLI headless, modelo `sonnet`, com `--safe-mode` e `--strict-mcp-config`.** Sem SDK de modelo, sem chave de API — não há credencial de IA no projeto. O usuário não escolhe modelo. Ver 6.0.
18. **Todo `claude` roda sem `Bash` e com `--add-dir` restrito a `.maestro/`.** Headless não tem quem responda prompt de permissão: autorize antes, no mínimo necessário. Ver 6.0.
19. **Criar processo é `execFile` com array de argumentos, nunca `exec` com string montada.** Vale em especial para o corpo do PR e o prompt da IA — os dois carregam texto gerado por modelo. Ver 8.1.
20. **Lint e format são Biome.** Não introduzir ESLint nem Prettier. A regra `noRestrictedImports` de 10.1 é arquitetural — se ela acusar, o certo quase sempre é mover o código, não abrir exceção.
21. **A IA edita o `.yml` direto em disco**, e o watcher fecha o loop. Não construir um caminho de edição paralelo para ela. Ver 6.2.
22. **Diante de ❓, perguntar** — não escolher em silêncio e seguir.
